# E11 — Партнёрский капитал как реальный счёт договора (единый источник правды денег)

**Статус:** `IN_PROGRESS`
**Прогресс:** ~60% (Фазы 1–3 DONE 2026-05-30; осталось 4 консолидация, 5 доки, 6 frontend)
**Зависит от:** E07, E08 (DONE)
**Блокирует:** корректный partnership-money flow; косвенно E03 (Net Value), E10 (UI пополнения/оплаты)

---

## Цель

Сделать капитал инвест-договора **реальным денежным счётом-пулом**: взносы физически двигают кэш в пул, оплата поставщика партнёрского прихода идёт из пула, баланс выводится из движений пула. Один источник правды денег; «все партнёрские деньги через договор» становится физической, а не только бухгалтерской правдой.

## Контекст и обоснование

Аудит (доки + код + БД, 2026-05-30) по симптому «деньги договора не видно в кассе»:

- **Факт БД:** договор #1 — взносы инвестор 10 000 + бизнес 4 000 USD с **0 cash-in** (чистый леджер без денег); договор #2 — взносы с cash-in. Несогласованность.
- **Корень — дрейф, не злой умысел:** взносы пишутся несколькими путями, часть леджер-онли (REST `views.py:112`, OWN_CASH); оплата поставщика партнёрки идёт из **обычной кассы** (`pay_workspace_supplier_payable`), а не из пула; `record_partner_capital_contribution_payment` кредитует 3100 независимо от роли (мис-атрибуция капитала оператора).
- Создание договора корректно (`CapitalCommitment`, план). Баланс выводится корректно (`InvestmentAgreement.balances` @property), но не подкреплён кэшом.
- **Канон по докам** (E07/E08/glossary/domain): деньги только через договор; «прямой оплаты мимо договора нет»; баланс выводится; `Payment.source_type=CAPITAL_POOL` как источник оплаты поставщика; раздельный аудируемый per-partner капитал (Mudaraba оператор=0; Musharaka убыток по доле). Код отъехал от канона.

**Решение основателя (2026-05-30):** Вариант 2 — реальный счёт-пул договора (см. «Решённые вопросы»).

## Сценарии (use cases)

- **US-1.** Инвестор вносит деньги → кэш реально приходит в пул договора (извне, EXTERNAL_PARTNER); операционная касса не меняется.
- **US-2.** Бизнес вносит «из своих оборотов» → transfer операционная касса → пул (касса ↓, пул ↑).
- **US-3.** Бизнес вносит «из кармана» (новые деньги) → cash-in в пул, как инвестор.
- **US-4.** Оплата поставщику партнёрского прихода → списание из пула (CAPITAL_POOL), не из операционной кассы.
- **US-5.** Баланс пула, per-partner капитал и журналы сходятся; «доступно» = реально доступный к развёртыванию кэш.

## План реализации (фазы)

### Фаза 1 — Модель + миграция
`InvestmentAgreement.capital_account` (FK → finance.CashAccount, kind=AGREEMENT_CAPITAL, валюта договора), создаётся per-agreement. Миграция: счёт-пул существующим договорам, opening balance = текущему derived available (договор #1 USD = 7 940), append-only.

### Фаза 2 — Единый сервис взноса (реальные деньги в пул)
Один сервис, три режима (investor-external / business-pocket-external / business-own-cash transfer); все двигают кэш в пул. Убрать леджер-онли пути. Роль-корректный счёт капитала (оператор ≠ 3100).

### Фаза 3 — Оплата поставщика из пула
Партнёрская оплата (`pay_workspace_supplier_payable` + AT_RECEIPT путь в `receive_workspace_batch`) списывает из пула, `source_type=CAPITAL_POOL`. OWN_FUNDS — из операционной кассы.

### Фаза 4 — Консолидация источников правды
Инвариант (тесты): баланс пула = из CashEntry; per-partner = из событий; сходятся. Сверка с `OwnerContribution`/`OwnerDrawing`.

### Фаза 5 — Доки / ADR
Обновить канон (E07/E08/glossary/domain/finance/partnerships): «капитал договора = реальный счёт-пул; баланс из его движений; оплата партнёрки из пула». Прежний «чистый леджер»-уклон → superseded 2026-05-30.

### Фаза 6 — Frontend + верификация
Переделать `PartnershipBudgetTopUpSheet` под реальную семантику; показать баланс пула; оплата из пула. Визуал модалки сохранить. E2E + reconciliation тесты.

## Решённые вопросы (история)

- ✓ 2026-05-30: журнальный счёт капитала оператора → **3000 (Собственный капитал)**, не 3100. Причина: оператор = владелец бизнеса; отдельного «капитала оператора» в плане счетов нет, а инвесторский капитал (3100/3110) — это партнёрская equity со стороны. Per-partner аудит капитала живёт в `AgreementContribution` + `ProcurementReceiveBatchCapitalAllocation`, GL лишь не смешивает инвесторские деньги с деньгами владельца.

- ✓ 2026-05-30: целевая модель партнёрского капитала → **реальный счёт-пул договора** (Вариант 2). Прежний «чистый леджер / derived-only баланс» уклон в доках E07/E08 → **superseded**: пул = реальный CashAccount, баланс выводится из его движений, оплата поставщика из пула. Причина: «деньги через договор» должны быть физической правдой + один источник правды денег.
- ✓ 2026-05-30: аудит подтвердил, что расхождение — дрейф (несколько путей записи взноса, оплата из кассы), а не сознательное смешение касс с инвесторскими деньгами.
