# E02 — Product–Supplier Links (UX + модель)

**Статус:** 🟡 `IN_PROGRESS` (проектируется параллельно с E01)
**Прогресс:** ~15% (модель утверждена, реализация не начата)
**Зависит от:** E01 (по UX-форме)
**Блокирует:** E03
**Параллельно:** E01, E04

---

## Цель

Связать товары с поставщиками — мягко, с поддержкой множественной связи и автоматическим обогащением связи в процессе работы. Это даёт **умную сортировку** в выборе товаров при приёмке и **корректную аналитику** «кто поставляет что» для E03 (отчёт о реальной ценности).

## Контекст и обоснование

В большинстве FMCG-кейсов один **поставщик** обычно поставляет **ограниченный ассортимент** (пекарня — хлебобулочные, дистрибьютор напитков — воды/соки и т.д.). Реже — но бывает — один и тот же товар приходит от разных поставщиков. Сейчас в системе **нет связи** между товаром и поставщиком (кроме исторической: «этот лот пришёл от этого поставщика»). Из-за этого:

- При создании прихода оператор листает **весь каталог** товаров, теряя время.
- Невозможно построить отчёт «какие товары мы берём у кого, в каком объёме, на каких условиях».
- Невозможно сравнивать поставщиков по позициям, пересекающимся между ними.

## Сценарии (use cases)

- **US-1.** Оператор открывает экран «Создать приход» → выбирает поставщика → видит каталог, где **сверху идут товары, ранее приходившие от этого поставщика**, потом остальные.
- **US-2.** Оператор создаёт новый товар прямо внутри прихода → товар **автоматически привязывается** к этому поставщику (как preferred/primary).
- **US-3.** Тот же товар поставляет второй поставщик (редкий, но реальный кейс) → при приходе от второго возникает **дополнительная soft-связь**, primary остаётся прежним (или можно поменять руками).
- **US-4.** Оператор в карточке товара видит список поставщиков, у которых он этот товар брал — с историей цен и условий.
- **US-5.** В карточке поставщика — список товаров, которые он поставляет, с аналитикой (объём, среднее количество в приёмке, доля в выручке магазина).

## Текущее состояние

- ✅ **Что уже есть:**
  - Модели `Product`, `ProductVariant`, `Supplier` независимые
  - Историческая связь через `Procurement → Supplier`: можно ретроспективно вытащить «этот товар приходил от этих поставщиков»

- ❌ **Чего нет вообще:**
  - Явной модели связи `ProductSupplier` (или эквивалента)
  - Признака primary supplier для товара
  - Сортировки каталога по preferred-связям в UX приёмки
  - Автообогащения связи при создании/приёмке товара

## План реализации

### Фаза 1 — Модель связи

**`ProductSupplier`** (NEW):
- `product_id`, `supplier_id` (composite unique)
- `last_received_at` (timestamp последней приёмки от этого поставщика)
- `last_unit_price`, `last_currency` (цена последней приёмки)
- `total_received_quantity` (суммарно когда-либо)
- `total_received_value_uzs` (в базовой валюте)
- `total_procurements_count` (счётчик приёмок)

**Никакого явного `is_primary` флага** — приоритет вычисляется на лету: `last_received_at DESC, total_procurements_count DESC`. Это решение зафиксировано в E01 (см. Решённые вопросы 2026-05-12).

**Soft-связь:** один товар → много поставщиков, один поставщик → много товаров. Связь **создаётся и обновляется автоматически**, никогда не удаляется руками.

### Фаза 2 — Автообогащение

Хук в сервисе `procurement.confirm()` (E01 T-1.6): для каждого `ProcurementItem`, у которого `procurement.supplier_id IS NOT NULL` — `upsert ProductSupplier`:
- если связи нет → создать с текущими значениями
- если есть → обновить `last_*` поля, инкрементить агрегаты

Хук в `inventory.quick_create_product(name, ..., from_procurement_id)`: при создании товара «на лету» в форме приёмки → сразу создать `ProductSupplier` с поставщиком этой приёмки.

### Фаза 3 — UX каталога в приёмке

Используется в Шаге 2 формы приёмки (E01 T-3.2). API:

```
GET /api/v1/inventory/products/?supplier_id=X&search=хлеб&order=preferred
```

Возврат: список товаров с сортировкой:
1. Товары с `ProductSupplier(supplier_id=X)` — по `last_received_at DESC`
2. Остальные товары — по релевантности поиска

В JSON каждого товара — `_supplier_link: { last_price, last_received_at, total_count }` или `null`.

### Фаза 4 — Аналитика

**Карточка товара:** список всех поставщиков, у которых брали этот товар, с историей: средняя цена, последний приход, общий объём.

**Карточка поставщика:** список всех товаров, которые он поставляет, с агрегатами: топ по объёму, средний чек приёмки, динамика.

Эти данные нужны для **E03** (Real Value Reporting) — без них нельзя сделать «сколько у нас товара лежит от каких поставщиков».

## Открытые вопросы

- ? Влияет ли связь на бизнес-логику в будущем (например, при низком остатке автоматически предлагать заказ у preferred-поставщика)? Сейчас — только UX, в будущем может расширяться.
- ? Bulk-импорт: если у клиента уже есть Excel с привязками товар↔поставщик — поддерживаем загрузку? (нерелевантно для MVP)
- ? Что показывать в UI, если у товара есть `ProductSupplier`-связи, но для текущего выбранного поставщика — нет? Бэйдж «впервые от этого поставщика»? Просто без бэйджа?

## Решённые вопросы (история)

- ✓ 2026-05-12: «Может ли один товар быть у нескольких поставщиков?» → да, редко, но бывает; модель multi-supplier
- ✓ 2026-05-12: «Primary supplier — флаг или сортировка?» → не делаем явный флаг, сортируем по `last_received_at DESC, total_procurements_count DESC`
- ✓ 2026-05-12: «Что считать связью — confirmed или draft?» → только **confirmed** Procurement. Draft в счёт не идёт.
- ✓ 2026-05-12: «Можно ли руками отвязать товар от поставщика?» → нет. Связь только обогащается; «отвязка» = просто старая связь без свежих приёмок, которая со временем уходит вниз сортировки.
