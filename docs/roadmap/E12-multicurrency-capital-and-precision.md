# E12 — Мультивалютный капитал договора (FIFO cost-basis) + точность расчётов

**Статус:** `IN_PROGRESS`
**Прогресс:** ~35% (Фаза 1 модель + Фаза 2 ядро FIFO/конвертация DONE 2026-05-31; осталось интеграция в оплату, точность-принцип, frontend)
**Зависит от:** E11 (DONE — реальный счёт-пул договора)
**Блокирует:** корректную секцию «оплата» в E10 (детальная страница прихода); косвенно E03 (Net Value), E06 (шариатская сертификация — точность/халяльность)

---

## Цель

Дать договору **одну валюту учёта** для долей/снапшотов (просто и однозначно),
но позволить пулу **физически держать и тратить деньги в разных валютах** через
реальную конвертацию (сарф), с **FIFO cost-basis** учётом стоимости валюты —
чтобы себестоимость товара на каждом приходе считалась по реальному курсу
приобретения денег, а не по рыночному курсу момента. Плюс зафиксировать принцип
**максимальной точности расчётов на бэкенде (без преждевременного округления)**.

## Контекст и обоснование

Сессия 2026-05-31 (после закрытия E11). E11 сделал капитал реальным счётом-пулом,
но **одновалютным**: взнос и оплата только в валюте договора. Реальность шире:

- Затраты прихода мультивалютны (товар в USD, налоги/логистика в UZS) → пул
  всё равно вынужден платить в разных валютах. Конвертация неизбежна.
- Сценарий подтверждён основателем как реальный: инвестор вносит USD, бизнес
  оперирует UZS из местных оборотов.
- Нельзя авто-конвертировать по курсу при оплате — это не отражает жизнь
  (человек реально меняет $1000, платит, часть остаётся). Конвертация —
  намеренное действие пользователя, реальный спот-обмен.

Без модели возникают две ловушки, которые этот эпик закрывает:
1. **Плавающая переоценка долей по курсу** — несправедлива (наказывает сторону
   за курс, в котором она не виновата). → **отвергнута**.
2. **Смешанные по валютам снапшоты** («инвестор $700 + 1млн, бизнес $100+200к»)
   — запутанно и нетестируемо. → снято за счёт единой валюты учёта.

## Сценарии (use cases)

- **US-1.** Договор в USD. Нужно оплатить налог в UZS → пользователь реально
  конвертирует часть пула USD→UZS (свой курс), платит из UZS-остатка; сдача
  остаётся в UZS-под-пуле для следующих UZS-расходов.
- **US-2.** Несколько конвертаций по разным курсам в пуле; трата идёт FIFO —
  самые ранние деньги первыми, base-стоимость расхода считается по курсам
  списанных лотов.
- **US-3.** Частичное оприходование: снапшот фиксирует base-стоимость затрат
  (прямые USD + UZS по FIFO cost-basis), доли — в одной валюте учёта.
- **US-4.** Доли участников **зафиксированы на момент взноса** и не
  переоцениваются при движении курса.

## Согласованная модель (канон эпика)

**Раздели два слоя:**

- **Слой капитала/долей = одна базовая (учётная) валюта договора.** Взносы —
  только в ней (ограничение E11 сохраняется). Доли фиксируются при взносе и
  **никогда не переоцениваются** курсом. Снапшоты всегда одновалютны.
- **Слой физических денег = мультивалютный** через реальную конвертацию.
  Конвертация НЕ трогает доли — меняет только физическую форму денег.

**FIFO cost-basis на валютных лотах конвертации:**

- Каждая конвертация = **лот**: `{валюта, курс, остаток_валюты, остаток_base, дата}`,
  append-only.
- Трата валюты списывает лоты **с самого раннего (FIFO)**; base-стоимость
  расхода = Σ по списанным лотам (по курсу каждого лота). Это и есть «журнал
  движения денег»: система знает, какой лот перечёркнут и из какого курса
  считать следующую трату.
- Снапшот/landed-cost берут **только** base-стоимость, отданную функцией траты
  (не рыночный курс дня приёмки) → опасная плавающая переоценка устранена
  конструктивно.

**Пример (3 конвертации по $1000):** L1 12М@12000 ($1000), L2 12.5М@12500
($1000), L3 13М@13000 ($1000). Трата 15М UZS → L1 12М=$1000 + L2 3М=$240 →
**base $1240**; в L2 осталось 9.5М ($760), L3 нетронут.

**Почему справедливо по шариату:** доля фиксируется на входе (стандартная
Мушарака); конвертация — реальный спот-сарф (халяль); base-капитал расходуется
по реальной цене приобретения валюты (cost-basis) → нет фантомной
прибыли/убытка на долях; append-only → аудируемо.

**Почему FIFO, а не среднее (решено 2026-05-31):** на доли метод не влияет
(доли залочены), но cost-basis тащится в **себестоимость лота товара** → цену и
в распределение убытка при браке/потере. FIFO даёт честную пер-лотовую
себестоимость по реальному курсу приобретения и консистентен с товарным FIFO
(одна ментальная модель). Нюанс: в естественном потоке «конвертировал→потратил»
FIFO и среднее совпадают; FIFO выигрывает на «накопил разные курсы→потратил
пачкой» и в аудируемости.

**Минимум точек контакта (чтобы не запутаться):** 2 функции + 1 журнал.
1. `convert_in` — обёртка над существующим `exchange_currency`, создаёт лот.
2. `spend_pool(валюта, сумма)` — списывает лоты FIFO, **возвращает base-cost**
   (единая точка выхода: любой платёж получает base-стоимость отсюда).
3. Лоты и списания append-only; сторно = новая корректирующая запись.

## Принцип точности расчётов (канон эпика)

- **Бэкенд считает с максимальной точностью, без преждевременного округления.**
  Не округлять промежуточные расчёты до 2 знаков; не использовать типы,
  дающие авто-округление/потерю точности в денежной математике.
- **Округление — только на уровне представления (фронт/отчёт), не в расчётах.**
- Точность «максимальная, но без фанатизма»: цель — не терять копейки на
  больших суммах и цепочках, а не уходить в избыточную псевдо-точность.
- Обоснование: позиционирование как точная партнёрская/шариатская финансовая
  платформа требует, чтобы партнёрские расчёты, себестоимость и распределение
  прибыли/убытка были корректны на больших суммах и длинных приходах.

## Как собирается приёмка/снапшот (зафиксировано 2026-05-31 — не развилка)

Снапшот и доли — **всегда в одной (базовой) валюте**. Никаких смешанных по
валютам долей между сторонами (этот вариант отвергнут). Сборка стоимости
прихода в базовую валюту:

- Затраты в **базовой** валюте → берутся напрямую (base = native).
- Затраты в **другой** валюте → списываются из под-пула этой валюты через
  `spend_pool_cost_basis` (FIFO) → их **base-стоимость по курсу конвертации**
  (не по рыночному курсу дня приёмки).
- Итог = Σ базовых стоимостей всех затрат → распределяется по долям в базовой
  валюте (дефолтное распределение система предлагает, как сейчас).

**Рабочий пример (основателя):** база USD. На товар $90 000 (USD-затрата →
$90 000 напрямую). Часть прочих затрат — в UZS: заранее конвертировали $3 000
тремя траншами (12 000 / 12 500 / 13 000) → 37 500 000 UZS в UZS-под-пуле.
Потратили из них, скажем, 30 000 000 UZS → их base-стоимость считается FIFO
(L1 12М@12000=$1000, далее по курсам лотов) ≈ $X. Снапшот: общая стоимость =
$90 000 + $X, **в долларах**, распределяется по долям. Физически: USD-затраты
ушли из USD-пула, UZS-затраты — из UZS-под-пула; не хватило валюты → сначала
конвертация (без авто-конвертации).

## Технические решения (2026-05-31)

- **Под-пулы = отдельный `CashAccount` на каждую валюту** под договором
  (переиспользуем одновалютную модель + готовый `exchange_currency`). Связка
  через partnerships-модель `AgreementCurrencyPool(agreement, currency,
  cash_account)`; базовая валюта = существующий `agreement.capital_account`.
  Не трогаем `CashAccount` (не делаем его мультивалютным — это задело бы всё).
- **FIFO-лот = `CurrencyConversionLot`** (partnerships, append-only факт
  конвертации; `amount_remaining`/`base_cost_remaining` — изменяемое running
  состояние, как `CashAccount.balance`/`LotStock.quantity_remaining`).
- **GL при конвертации:** обе ноги книжатся равной functional-суммой (base_cost
  в UZS-эквиваленте) → нет фантомной курсовой в GL; cost-basis несёт правду,
  mark-to-market не делаем.
- **Точность в E12:** новые поля (rate, base_cost) — высокая точность
  (≥6 знаков); промежуточные расчёты cost-basis НЕ квантуем до 0.01.
  Широкий ретрофит существующих 2-знаковых money-полей = T-3.2 (по подтверждению
  основателя), в E12 не делаем.

## Frontend (план — затрагивается)

E12 меняет не только бэк. В секции «оплата» детальной страницы (E10):
- Показ **остатков пула по валютам** (под-пулы), не один баланс.
- Действие **«Конвертировать»** (реальный сарф): из валюты пула в нужную, по
  курсу пользователя; видны лоты/остатки. Переиспользует `exchange_currency`.
- Оплата расхода идёт из под-пула нужной валюты; не хватает → подсказка
  «сначала конвертируйте». Без авто-конвертации.
- Взнос (`PartnershipBudgetTopUpSheet`) остаётся в валюте учёта (как сейчас).
