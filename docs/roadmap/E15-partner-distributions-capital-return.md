# E15 — Partner Distributions & Capital Return (outbound partner money)

**Статус:** `IN_PROGRESS` (дизайн зафиксирован 2026-06-03)
**Прогресс:** 90% — Фазы 1–4 + карточка договора (взаиморасчёты + дивиденд + возврат) +
отчётная интеграция + ADR готовы и протестированы. Остаётся только **живой прогон
mobile/desktop** карточки (зона основателя).
**Зависит от:** E11 (пул), E12 (мультивалюта), E14 (авансы — FROM_PROFIT встраивается сюда)
**Блокирует:** завершение E14 (T-3.2 FROM_PROFIT), корректность E03 (Net Value)

---

## Цель

Сделать **исходящие** партнёрские деньги реальными и едиными: возврат недоразвёрнутого
капитала и распределение накопленной прибыли (дивиденды) физически двигают кэш и пишут
проводки, append-only, без «магических» изменений баланса. Сегодня это либо леджер-онли
(вывод капитала не трогает кэш пула — нарушение инварианта), либо с неверной проводкой
(дивиденд, counterpart 2100), либо не реализовано вовсе.

## Контекст и обоснование (аудит 2026-06-03)

- **Возврат капитала** (`add_agreement_withdrawal`, `workspace_support.py`): сервис+endpoint+
  UI-форма есть, но **кэш из пула НЕ уходит, проводки нет** — `AgreementWithdrawal` только
  запись. Пул `CashAccount.balance` никогда не уменьшается → расходится с derived `balances`.
  Прямое нарушение «деньги двигаются только реально».
- **Дивиденд** (`pay_dividend`, `agreement_services.py:176`): кэш опционален (только если задан
  `from_account_id`); journal counterpart захардкожен `2100` (неверно для распределения
  прибыли); нет workspace-action; **нет frontend**.
- **Прибыль партнёра**: только суб-леджер `PartnerLedgerEntry` (PROFIT_ACCRUED, UZS); деньги с
  продаж ложатся в операционную кассу (DR 1000/CR 4000); GL не атрибутирует прибыль по
  партнёрам.
- **Недоразвёрнутый капитал**: физически лежит в пуле после развёртывания; механизма возврата
  нет (вывод — леджер-онли).
- **COA уже содержит:** `1300` пул, `3000`/`3001` владелец/изъятие, `3100`/`3110` инвест-капитал,
  `3200` нераспределённая прибыль, `2100` задолженность перед инвесторами.

## Сценарии (use cases)

- **US-1.** Внесли 15 000, развернули в приходе 13 000 → остаток 2 000 в пуле. Возврат 2 000
  партнёрам (pro-rata) — реальный кэш из пула, записанный документ. Пул ↓, equity ↓.
- **US-2.** По мере продаж копится прибыль; инвестор просит выплату накопленной чистой
  прибыли (напр. 2 000) до полной распродажи — бизнес выдаёт из операционной кассы. Инкрементально.
- **US-3.** Гашение аванса из прибыли (E14 FROM_PROFIT): прибыль должника не идёт ему в карман,
  а гасит его межпартнёрский долг (капитал достраивается, кредитор получает возврат).
- **US-4.** Любое исходящее — append-only, с проводкой, идемпотентно; баланс не меняется «вдруг».

## Целевая модель

**Симметрия INBOUND/OUTBOUND через пул/кассу. Два РЕАЛЬНЫХ типа исходящего (разные источники
и проводки), единый UX-концепт «выдать партнёру».**

### Тип 1 — Возврат капитала (`AgreementWithdrawal`, сделать физическим)
- Источник: **пул** (там лежит недоразвёрнутый капитал).
- Проводка: **DR 3100/3110/3000 (equity партнёра по роли) / CR 1300**, `CashEntry OUT` из пула.
- Гард: ≤ недоразвёрнутого капитала партнёра (derived available), ≤ физического баланса пула.
- Добавить `paid_to_account_id` (необяз.) — куда ушёл кэш (касса инвестора), иначе просто отток.

### Тип 2 — Распределение прибыли / дивиденд (`DividendPayment`, сделать физическим + верный GL)
- Источник: **операционная касса** (деньги с продаж).
- `destination`: **TO_PARTNER** (в руки/счёт) | **TO_ADVANCE** (гасит `CapitalAdvance` — E14).
- Кэш обязателен (убрать «опционально»). Гард: ≤ profit_pending партнёра.
- Проводка TO_PARTNER: **DR 3200 (нераспред. прибыль) / CR 1000/1010**, `CashEntry OUT`.
  (3200 уходит в минус до закрытия периода — приемлемо; полный close revenue→3200 — забота E03.)
- Суб-леджер: `DIVIDEND_PAID` партнёру.

### FROM_PROFIT (E14 T-3.2) = распределение прибыли → TO_ADVANCE
Прибыль должника гасит его аванс. Проводка:
- **DR 3200** (профит должника потреблён) **/ CR 3100/3110** (капитал должника достроен)
- **DR 3000** (возврат кредитору) **/ CR 1000** (касса кредитору), `CashEntry OUT`
- Суб-леджер: `DIVIDEND_PAID` должнику; `CapitalAdvanceSettlement(source=FROM_PROFIT)`.
Тело-only, ≤ min(profit_pending должника, outstanding аванса).

### Принципы
- Никакой магии: каждое уменьшение — явный append-only документ.
- Всё через договор/пул (#13), с проводкой (#10), append-only (#12), идемпотентно.
- Возврат капитала из пула; прибыль из операционной кассы — два источника не случайны.

## План реализации (фазы)

### Фаза 1 — Возврат капитала физическим
`add_agreement_withdrawal` двигает кэш из пула (`record_capital_pool_payment`-стиль, counterpart
= equity-счёт партнёра) + journal + гарды (≤ доступного, ≤ пула). Pool-инвариант восстановлен.

### Фаза 2 — Распределение прибыли физическим + верный GL
`pay_dividend`: кэш обязателен, counterpart 3200 (не 2100), `destination` поле. Гард ≤ pending.

### Фаза 3 — FROM_PROFIT (закрывает E14 T-3.2/T-4.2)
`settle_capital_advance(source=FROM_PROFIT)` → распределение прибыли должника на аванс.
Авто-гашение при распределении, если `repayment_mode=FROM_PROFIT`.

### Фаза 4 — Endpoints + workspace actions
`RETURN_CAPITAL` / `PAY_DIVIDEND` / `SETTLE_ADVANCE` в ACTION_MAP; REST для авансов и выплат.

### Фаза 5 — Frontend (зона основателя по приходу; карточка договора — собрать)
Карточка инвест-договора: «Взаиморасчёты» (авансы + погасить), «Выплаты» (возврат капитала,
дивиденд), остаток/доступно. Существующую форму вывода починить под реальную семантику.

### Фаза 6 — Отчёты + ADR + живой прогон
Исходящие в cash-flow/отчётах; ADR; верификация основателем.

## Решённые вопросы (история)

- ✓ 2026-06-05: куда идут деньги при погашении аванса? → **Модель B (пул — единственный хаб).**
  Погашение = деньги падают в **пул договора** (для CASH — это реальный взнос должника через
  `add_agreement_contribution`, для FROM_PROFIT — профит реинвестируется как капитал +
  запись взноса для сходимости), долг ↓. Кредитор НЕ получает авто-возврат — забирает свою
  переплату **отдельным выводом капитала**, когда захочет. Раньше (Model A) погашение
  авто-выталкивало кэш кредитору, склеивая два разных решения и лишая сделку оборотных денег.
  Деньги двигаются только через договор (#13); пул физический сходится с derived-балансом.


- ✓ 2026-06-03: единая сущность для исходящего или две? → **Две реальные** (возврат капитала
  из пула vs дивиденд из операционной кассы — разные источники/проводки), **единый UX-концепт**.
  Это best practice distribution waterfall (return of capital tier ≠ profit tier). FROM_PROFIT =
  дивиденд с destination=TO_ADVANCE.
- ✓ 2026-06-03: counterpart прибыли? → **3200 (нераспределённая прибыль)**, не 2100. Полный
  per-partner profit-payable accrual — позже (E03).
