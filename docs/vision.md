> принципами руководствуемся. **Не roadmap** (тот в [`ROADMAP.md`](./ROADMAP.md))

## Где мы сейчас (MVP)

POS-платформа для мелкого ритейла с уникальным слоем: **финансово-партнёрский
учёт поверх продаж**. Автоматический partnership accounting (мудараба,
мушарака), FIFO-распределение прибыли/убытков по immutable lot snapshot-ам,
прозрачные dashboards для инвесторов и партнёров.

Это не «ещё один POS». Это POS, в котором инвест-партнёрство — first-class
сущность, а не Excel-надстройка.

## Куда мы идём (3 горизонта)

### Горизонт 1 — Operational system для ритейла

POS превращается в **операционную систему мелкого/среднего бизнеса**.
Помимо продаж и инвент-учёта система ведёт:

- весь cash flow (текущий + прогнозный с учётом будущих обязательств)
- net value бизнеса (cash + inventory at cost + receivables − payables − capital owed)
- кредиторку/дебиторку по всем поставщикам/клиентам/инвесторам
- обязательства по графикам (отсрочки, рассрочки, консигнация)
- ранние сигналы: близится кассовый разрыв, заканчивается оборотка по
  товару, маржа падает в сегменте

Цель — пользователь открывает приложение и видит не «сколько продали за
сегодня», а **состояние бизнеса целиком** с подсветкой того, что требует
внимания.

### Горизонт 2 — AI-ассистент

Над собранными данными — слой объяснения и рекомендаций. Не «чат с
выгрузкой Excel», а нормальный диалог: «почему у меня в апреле упала
маржа?», «стоит ли мне сейчас брать большой заказ воды у дистрибьютора —
потяну ли?», «что подсказывают цифры на ближайший месяц?». Источник данных —
тот же канонический набор append-only событий, что и для дашбордов.

### Горизонт 3 — Marketplace инвесторов

Отдельный продукт в экосистеме. Каталог бизнесов, которые сидят в системе и
готовы привлекать инвестиции. Анализ потенциального инвестора строится на
real-time метриках бизнеса: оборачиваемость, маржинальность, return rate,
сезонные паттерны. Под капотом — переиспользование того же partnership-стека
(InvestmentAgreement, мудараба/мушарака).

Конкретный сценарий, который оправдывает наличие маркетплейса: сезонные
закупки (вода/напитки летом), где дистрибьюторы не дают отсрочку. Без
маркетплейса бизнес упускает сезон; с маркетплейсом — находит инвестора под
конкретный приход, и обе стороны зарабатывают.

## Архитектурные принципы (то, что не обсуждается)

1. **Architecture-first delivery.** Не пишем тесты ради тестов, не строим
   shim-ы под legacy, не делаем компромиссы под локальный «зелёный»
   результат. Любое решение оценивается не «работает ли сейчас», а «как
   оно живёт в долгую под нагрузкой и при расширении».
2. **Append-only ledger для всего, что касается денег.** Reversal — это
   новая запись, не delete. История не переписывается. Это нужно и для
   шариатского аудита, и для будущего AI-слоя.
3. **Immutable snapshot.** Раз зафиксированная доля капитала в Lot или
   договоре не пересчитывается при изменении окружения. Прошлое — данность,
   корректировка — новый документ.
4. **Derived > stored.** Балансы, обязательства, outstanding — считаются из
   событий. Никаких параллельных «таблиц с агрегатами», которые могут
   расходиться. (E08 закрыл эту дисциплину.)
5. **Independent axes, not enum-soup.** Бизнес-сценарии моделируются через
   независимые оси (источник денег × время оплаты × владение товаром), а
   не через большой enum типов. Любая новая комбинация — либо валидная
   точка в существующих осях, либо нужна новая ось, не новый enum.
6. **Sharia-compliance built-in.** Не плагин, не настройка. Инварианты
   шариатского учёта (Σ shares = 1.0, FIFO-snapshot, мудараба/мушарака
   через одну агреемент-сущность) — структурно неотменяемы.

## Что VISION НЕ описывает

- Конкретные UI-экраны и flow → roadmap + design сессии.
- Технические эпики и их чек-листы → `docs/roadmap/`.
- Имена полей, миграции, контракты API → доменная документация.
- Краткосрочные приоритеты на месяц → `ROADMAP.md` в разделе «Активный P0».

## Когда переписывается этот документ

- Когда меняется один из 3 горизонтов (например, маркетплейс заменяется на
  что-то другое).
- Когда добавляется/удаляется архитектурный принцип.
- Когда формулировка «не ещё один POS, а финансово-партнёрский слой» теряет
  актуальность.

Переписывание — отдельное событие, фиксируется датой. Промежуточные правки
не делаются — это якорь, а не живой документ.
